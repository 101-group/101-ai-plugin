# CRM: оркестрация 21 операции

Этот ресурс задаёт решения до вызова инструмента. Точную JSON Schema аргументов всегда читай из текущего tool catalog. Не переноси GUID в обычный ответ: разрешай сущности по человеческим названиям, а технические идентификаторы держи только в контексте вызова.

## Общий порядок

1. Получи пользователя и компанию через `whoami`, если контекст ещё не закреплён.
2. Определи домен и явное действие: read, create, edit, move, reorder или delete. Рекомендация и обсуждение не разрешают write.
3. Выполни безопасные read-вызовы из таблицы. Одно точное совпадение выбирай автоматически; несколько совпадений покажи по названиям с различающим контекстом.
4. Если обязательный смысл не задан, задай один минимальный вопрос. До ответа не вызывай write-инструмент. Не спрашивай GUID и не заставляй человека повторять данные, уже полученные чтением.
5. Непосредственно перед write перечитай изменяемое состояние. Для payload полного списка сравни свежий снимок с исходным; конфликт блокирует запись.
6. После write используй ответ как квитанцию и выполни указанное контрольное чтение. Сообщай человеческие имена и фактический результат.

## AI-generated rules: реальный формат

Правила применяются только при создании сделки без `responsibleGuid`. Backend перебирает активные правила по `sortOrder` и выбирает первое подходящее активное правило с доступным кандидатом. Явный `responsibleGuid` означает ручное назначение и обходит правила. Если подходящего правила или доступного кандидата нет, создание сделки завершается ошибкой; частично созданной сделки не остаётся.

`condition` имеет ровно два корневых ключа: `version` и `expression`. Узел `expression` использует `op`; логические узлы имеют форму `always`, `and` с непустым `items`, `or` с непустым `items` или `not` с `item`. Предикат содержит `field` и `op`; `value` обязателен только для операторов, чей `valueKind` не равен `none`. Для `in` и `notIn` значение является непустым массивом. Поля, допустимые для них операторы, типы, options и limits бери только из актуальной schema, полученной `get_crm_distribution_rule_schema`; не генерируй их из памяти.

Текущий backend поддерживает логические коды `always`, `and`, `or`, `not` и предикаты `eq`, `notEq`, `in`, `notIn`, `contains`, `notContains`, `startsWith`, `endsWith`, `gt`, `gte`, `lt`, `lte`, `exists`, `notExists`. Не каждый оператор подходит каждому полю: используй только `operators` конкретного поля из свежей schema. Встроенные пути сейчас: `source.uuid`, `source.type`, `source.name`, `source.isActive`, `funnel.id`, `deal.name`, `deal.preLead`, `deal.hasContact`, `contact.guid`, `createdBy.guid`, `createdAt.hour`, `createdAt.weekday`, `createdAt.isWeekend`; пользовательские поля имеют вид `customField.<code>`. Этот список — пояснение формата, а не замена schema.

`assignment` содержит `strategy` и непустой `candidates`. Текущие коды стратегий: `fixed`, `roundRobin`, `weightedRoundRobin`, `leastActive`. Каждый кандидат содержит `responsibleGuid` из `availableCandidates`; `weight` допустим только когда выбранная стратегия из schema поддерживает веса. Не подставляй GUID по имени и не используй сотрудника, отсутствующего в `availableCandidates`.

## AI-generated rules: обязательный preflight

До любого create, edit или reorder выполни строго эту последовательность:

1. Вызови `get_crm_distribution_rule_schema` для выбранной воронки.
2. Вызови `list_crm_distribution_rules` и сохрани текущий полный порядок.
3. Переведи просьбу пользователя в candidate rule, используя только текущую schema.
4. Задай один компактный блок вопросов по всем существенным пробелам. До ответа не вызывай ни один mutating tool.
5. Проверь точный синтаксис и типы; доступность полей, options, этапов и кандидатов; timezone; limits; уникальность кандидатов; допустимость весов; итоговый порядок.
6. Сравни условия со всеми более приоритетными и последующими активными правилами. Отметь очевидные пересечения, недостижимые ветви и правила, полностью затенённые более ранним `always` или доказуемо более широким условием.
7. Проверь полноту покрытия. Если её нельзя доказать для всех входов, потребуй явный fallback с `always` в конце. Без fallback не вызывай write: иначе backend отклонит создание любой сделки без `responsibleGuid`, которая не совпала с активным правилом.
8. Человеческая интерпретация: покажи «сначала проверяем …; при совпадении назначаем … способом …; иначе переходим к …; fallback …». Рядом перечисли результат проверок и ограничения доказательства.
9. Получи явное подтверждение именно этой интерпретации. Только после него вызови `create_crm_distribution_rule`, `edit_crm_distribution_rule` или `reorder_crm_distribution_rules`.
10. Используй ответ write-вызова и затем снова вызови `list_crm_distribution_rules`, чтобы проверить round-trip доступных полей и фактический порядок.

Fallback — отдельное правило с условием `always`, а не поле специального правила. Если подходящего fallback ещё нет, план его создания и настройку целевого правила считай неатомарной последовательностью: API не предоставляет общего transaction endpoint. Покажи порядок всех вызовов, payload каждого правила и временное влияние на назначения; получи одно явное подтверждение всего точного плана. Это согласие покрывает только показанные вызовы и payload. После каждого write перечитай `list_crm_distribution_rules` и повтори preflight следующего шага по свежему состоянию. При расхождении или ошибке остановись и сообщи частичный результат; не продолжай и не обещай автоматический rollback.

Backend валидирует структуру DSL, версию, поля, операторы, типы, limits, timezone, кандидатов и ссылки на текущую воронку. Отдельного validate, dry-run или simulation endpoint не существует. Backend не доказывает взаимную исключительность условий, достижимость всех ветвей или полное покрытие. Выполняй консервативный статический review по текущей schema и списку правил; если вывод нельзя доказать, пометь его как неопределённый и задай вопрос. Не обещай симуляцию реальных сделок.

## Каталог наводящих вопросов

Фраза «распределяй сделку на Марка до 12 часов» неполна. Одним компактным блоком выясни часовой пояс и остальные условия:

- в каком часовом поясе понимать «до 12»;
- что делать после 12 и нужен ли отдельный fallback;
- какие дни недели входят в правило;
- кто такой Марк среди `availableCandidates`;
- что делать, если Марк недоступен или больше не является менеджером воронки;
- к каким источникам, этапам и типам сделок относится правило;
- какое место правило занимает относительно существующих пересекающихся правил.

Для нескольких кандидатов дополнительно выясни стратегию человеческими словами: один ответственный, по очереди, по очереди с весами или наименее загруженному. Веса спрашивай только для стратегии, которая поддерживает их по текущей schema.
